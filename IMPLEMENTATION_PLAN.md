# Autonomous Job Application Bot: Implementation Plan

## Goal

Run a continuously available assistant that finds relevant jobs, prepares truthful applications, tracks submissions, and reports employer updates.

## Credentials and secrets

- **Local LLM:** No model-provider API key is needed. Both workers use the OpenAI-compatible local endpoint configured by `LOCAL_LLM_BASE_URL` (Compose defaults to `http://host.docker.internal:11434/v1`). Discovery uses `LOCAL_LLM_MODEL=gemma4:e2b`; application form interpretation uses `APPLICATION_LLM_MODEL=gemma4:e4b`. Send only the minimum public listing or approved candidate facts needed for the current task. Never send credentials, passwords, OAuth tokens, site logins, or other secrets to a model or log them.
- **Gmail and Google Sheets:** Create a Google Cloud project, enable the Gmail and Sheets APIs, and configure OAuth credentials. The app needs a client ID, a client secret for a server-side OAuth flow, and a locally stored user-authorized refresh token; this is OAuth, not a Google API key. Gmail read access requires `gmail.readonly`, which Google classifies as a restricted scope ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)).
- **ntfy.sh:** Configure the server URL and topic. Basic publishing to an open topic does not require an API key, but the topic name is effectively a secret; use an authenticated access token for a protected topic or self-hosted server ([ntfy publishing authentication](https://docs.ntfy.sh/publish/)).
- **Vaultwarden via Bitwarden CLI:** Configure the Vaultwarden server URL and the Bitwarden personal API `client_id` and `client_secret`. CLI access to encrypted items also requires vault unlock material; the API key alone does not unlock the vault ([Bitwarden CLI API key](https://bitwarden.com/help/personal-api-key/)). Keep this account limited to the bot's job-site credentials.
- **Optional live Excel:** If using a workbook in OneDrive or SharePoint, configure Microsoft Graph OAuth credentials and delegated user consent. A local `.xlsx` export needs no Microsoft credential.
- **Job sites:** No general scraping API key is required. Any site-specific API credentials or login credentials are separate and should be added only for approved sources and accounts.

## Main components

1. **Job discovery and matching**
   - Collect listings from web-search services, official job APIs, feeds, and sources that permit automated access. The discovery worker supports per-user keyword searches through a private SearXNG service and optional Adzuna credentials, configured HTTPS RSS/Atom feeds, and configured public job pages. Its page scraper honors robots.txt and extracts schema.org JobPosting records from a bounded set of same-host job links; it does not evade access controls. A collection page returned by SearXNG can seed a bounded two-level same-host crawl, but never becomes an application target. JavaScript-only job boards and source-specific parsers remain future work.
   - Let a user add multiple job fields or phrases, such as nursing and engineering internships, with optional locations. These searches direct collection; saved preferences remain soft ranking hints. Use local `gemma4:e2b` to classify public search results and a local text embedding model to rank matches. The discovery classifier receives only the visible result title and snippet, has a strict system prompt, and rejects uncertain or malformed responses; no raw SearXNG result is queued when classification is unavailable. Embedding scores are advisory and do not filter listings.
   - Never invent qualifications, experience, or answers.
   - Run discovery and application as two separate small workers. The scraper worker discovers, matches, and enqueues; the applier worker consumes eligible queue items and marks them complete only after confirmed submission.
   - Save public discovered listings by exact full URL in a global pool shared across accounts. Keep source phrases, profile matching, application state, notes, and leases in each user's private database. Let a user add a pooled public job to their own queue without inheriting another user's application state. Manually entered jobs stay private unless the user explicitly chooses to share the public listing.
   - Enqueue idempotently: if the exact full URL or a confirmed employer job ID already exists for that user, refresh the existing record and do not create another queue item. Keep company/title similarity as a possible-duplicate review signal.

2. **Complete per-user candidate profile and answer bank**
   - Provide one comprehensive, saveable profile form in the web UI. Let users complete it gradually, see completion gaps, and approve a version before the applier uses it. Keep each user's profile encrypted and isolated.
   - **Identity and contact:** legal first, middle, and last names; suffix; preferred name; pronouns (optional); email addresses; phone numbers; current and mailing addresses; country and time zone; preferred contact method; and approved professional profile links (LinkedIn, GitHub, portfolio, personal site, and work samples).
   - **Application materials:** master resume; role- or country-specific resume versions; user-approved professional summary, headline, objectives, and cover-letter templates; writing samples; publications; patents; presentations; and portfolio/work-sample URLs. Let users upload a PDF, DOCX, or text resume, paste or edit its text, or do both. Extract readable text locally when possible and offer only explicit facts as draft suggestions for user review. Preserve each document's version and approval status.
   - Treat automatic field suggestions from resume parsing as optional. Before preparing an application, the applier must load and read the text of the exact approved resume file selected for that job, identified by its document ID and checksum. Never substitute another resume's text or rely on profile suggestions as a proxy. If that file has no trustworthy readable text, pause for user-supplied text or OCR and approval before using it; do not guess its contents.
   - **Employment history:** for each position, employer and department, title, location/work arrangement, employment type, start/end dates, current-role flag, responsibilities, accomplishments and measurable outcomes, technologies/tools, manager/contact details when supplied, permission to contact the employer, rehire status, and user-approved reason for leaving. Include internships, contract work, self-employment, military service, volunteering, and career breaks when the user chooses.
   - **Education and training:** schools and locations, attendance dates, completed/in-progress status, degree or credential, field of study, GPA and grading scale if approved, honors, coursework, bootcamps, apprenticeships, and other training.
   - **Skills and evidence:** skills, proficiency, years or level of experience, last-used date, supporting role/project, tools and methods, spoken/written languages and proficiency, awards, projects, leadership, community work, and professional memberships.
   - **Licenses and certifications:** name, issuer, jurisdiction, issue/expiry dates, status, and optional credential number. Include driver's-license class and travel/vehicle availability only when the user chooses to provide them.
   - **Work authorization and eligibility:** countries where the user is authorized to work, the exact user-selected status wording, whether sponsorship is needed now or later, known authorization expiry dates, and any user-confirmed clearance or export-control eligibility. Never infer citizenship, immigration status, or eligibility from a name, address, or resume.
   - **Job preferences and constraints:** preferred and less-preferred titles, seniority, industries and employers, locations, remote/hybrid/onsite preference, commute radius, relocation willingness, employment types, schedule/shifts/weekend/overtime availability and time zone, travel limits, earliest start date, notice period, compensation minimum/target and separate base/bonus/equity/benefit terms, currency and pay period, company-size preferences, additional free-form preferences, and explicit hard dealbreakers. Users can add multiple preferences without making them mandatory.
   - Treat ordinary job preferences as soft signals for search expansion, ranking, and explanation. Show worthwhile matches outside the preferred titles, locations, arrangements, or compensation range instead of silently dropping them. Only a user-marked hard dealbreaker or a verified eligibility/source-policy restriction automatically blocks an application. If a job requirement conflicts with a known availability or other supplied fact, pause for review rather than misstate it; uncertainty requires review rather than a guessed exclusion. Current discovery ranking may flag a possible dealbreaker for review but does not automatically block or discard it.
   - **Reusable screening answers:** preferred compensation wording and salary-history response; start date and availability; travel, shift, commute, overtime, and relocation answers; sponsorship/work-authorization answers; how the user heard about the employer, referral source, prior employment/application, relatives at the company, and outside-employment answers; conflicts of interest or non-compete disclosures; background/drug-screening answers (explicitly approved); years of experience by skill; reasons for interest in a role/company; strengths and career goals; user-approved accomplishment stories; and any other question/answer pair the user explicitly approves for reuse. Store the original question, approved answer, source facts, date last confirmed, and reuse policy.
   - **References:** name, role, organization, relationship, contact details, preferred contact method, and whether the reference has agreed to be contacted. Never offer or contact a reference without the user's approval.
   - **Sensitive disclosures:** keep voluntary demographic/self-identification answers (such as race/ethnicity, sex/gender, disability, veteran status, and accommodation requests) in a separate optional section. Store only the user's explicit selections; never infer them. Default to blank or “prefer not to answer” where available. Treat age/date of birth, salary history, criminal-history answers, medical/accommodation information, drug-screening answers, security-clearance details, and similar disclosures as sensitive and require explicit user approval for each answer category.
   - **High-risk onboarding data:** do not keep Social Security/national ID numbers, tax IDs, passport scans, bank/payment details, health diagnoses, or identity documents in the general profile. If a site unexpectedly requests them, pause for a secure human handoff. Employment/tax onboarding after an offer belongs in the employer's secure process.
   - For every answerable field, distinguish `known`, `unknown`, `not applicable`, and `withheld`. Leave fields blank by default; a supplied value becomes `known`, while a blank value stays `unknown` unless the user optionally marks it not applicable or withheld. Keep reuse policy out of the ordinary form: approved everyday facts can be reused, while voluntary disclosures, references, and other sensitive answers require review. Use only user-confirmed facts and approved answer templates. Pause when a required field is unknown or unapproved.
   - Pause for e-signatures, legal attestations, background-check authorizations, medical consents, or agreements that certify facts or create obligations. Do not accept or sign these on the user's behalf by default.

3. **Persistent browser worker**
   - Use a dedicated, headed Chromium session controlled through CDP for page and form interaction. Use local `gemma4:e4b` to interpret bounded form labels and controls and select exact approved reusable candidate facts. Keep model-written narrative answers out of submissions until the user approves a reusable answer. Inspect one explicit same-host Apply link when a listing has no application form, after checking the linked public URL and robots.txt; retain the original listing URL as the ledger key.
   - For application CAPTCHA or sign-in verification, pause automation and retain that user's application browser session for a person. Start a temporary VNC/noVNC connection only in the applier, publish it on host loopback, show a direct browser-view link at the top of the owning user's queue page and on the job's history page, reveal its random password only on that user's history page, and close the browser when the user resolves the handoff. The current applier supports one live handoff at a time. Discovery has no VNC process or port.
   - For automatic submission, require the submit-eligible mode, an approved current profile and primary resume, and an available daily application allowance. Apply across queued job hosts without a separate host allowlist. The applier model may interpret a field and phrase an answer only from the relevant approved facts and exact approved answer-bank entries supplied for that task; it must not infer or create qualifications, work history, eligibility, or screening answers. Preserve `known`, `unknown`, `not applicable`, and `withheld` as distinct states. Send no secrets or unrelated candidate data to the model. Pause for unknown or unapproved required answers, attestations, signatures, sensitive disclosures, multi-step or ambiguous forms, site blocks, and verification challenges. Confirm the result before marking applied.
   - Stop when a site blocks automation or presents a visible interactive CAPTCHA or other human-only step; hidden integrations and passive reCAPTCHA badges alone do not count as a challenge. Hand control to a person and do not bypass the site's controls.

4. **Durable application tracking and recovery**
   - Store each listing's exact full URL and its state in a database: `discovered`, `in_progress`, or `applied`.
   - Record the URL before starting. Mark a job `applied` only after confirming submission.
   - On restart, revisit `in_progress` URLs and check whether the application was submitted before deciding whether to resume or retry. Keep an audit trail to prevent duplicate applications.
   - Before preparing or submitting an application, call `find_existing_application` against the durable history. Return confirmed matches for an exact full URL or employer job ID, and flag company/title matches as possible duplicates for review rather than silently treating them as the same job.
   - Back the workers with a durable per-user SQLite queue. Use transactional leases, heartbeats, attempt counts, retry delays, and a review/dead-letter state. A crashed worker's lease expires and the next worker recovers from the saved record and exact URL.
   - If a worker exits during submission and the outcome is uncertain, verify the site state before retrying; never blindly submit again. Mark the queue item done only when the application ledger records a confirmed submission.
   - Start each job with a fresh LLM context. Discard transient conversation history, tool results, and task scratch data after each attempt or abnormal exit. Preserve the durable queue, event log, user profile, secrets, and per-user browser login profile needed for recovery.
   - If a leased job URL is dead or does not lead to the expected posting before application work begins, the applier requests a rescrape for that one pooled job, pauses its private queue item, discards its task context, and claims the next item. A request must never erase application history. Discovery rechecks only an exact URL covered by a currently permitted public job-page source and robots.txt. Resume the private item only after the same exact URL has a verified JobPosting; a changed URL or uncertain identity needs review. If application work already began, review the submission outcome instead of skipping it.

5. **Gmail update scanning**
   - Connect with Gmail OAuth using read-only access.
   - Periodically scan for confirmations, interview requests, and status changes, and associate messages with tracked applications.
   - The initial `scripts/sync_gmail.py` adapter searches a configured Gmail query and stores deduplicated message headers in a private SQLite database; it does not fetch bodies/snippets and redacts verification-like subjects.
   - The same access can expose email verification codes, but `gmail.readonly` grants broad access to mailbox messages and settings, not just one-time codes ([Gmail API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)). If enabled, only search recent messages from approved senders, never log or store the codes, and surface them for human handoff instead of automatically using them to get past a site's verification or anti-bot step.

6. **ntfy.sh notifications**
   - Send alerts for confirmed applications, important Gmail updates, human handoffs, and worker failures.
   - Keep ntfy credentials in secrets configuration and avoid putting sensitive application or email contents in notifications.
   - The local deployment now includes a self-hosted ntfy container with persistent storage, a random topic, and a topic-only ACL. Its host port is loopback-only pending HTTPS reverse-proxy configuration.

7. **Editable spreadsheet tracker**
   - Offer a live Google Sheets workbook as the primary shared tracker. The Sheets API can read and update values and apply spreadsheet formatting; use user-authorized access with the narrowest suitable permissions ([Google Sheets API](https://developers.google.com/workspace/sheets/api/guides/values), [Sheets API scopes](https://developers.google.com/workspace/sheets/api/scopes)).
   - Organize it into a **Dashboard**, **Applications**, and **Review Queue**. Use frozen headers, filters, clear status colors, dropdowns, summary counts, and clickable job links.
   - Show company, role, location, match, application status, submitted date, last email update, next action, and the exact full job URL. Keep user-owned columns such as notes and priority separate from bot-owned columns so syncs do not overwrite edits.
   - Give the LLM narrow structured tools backed by the database and Sheets API, not raw cell/range access. Provide actions such as `find_existing_application`, `upsert_application`, `get_review_queue`, and `update_application_status`; validate fields and update only bot-owned columns. Read user-owned review decisions, priority, and notes without overwriting them.
   - Use the exact full job URL as the visible spreadsheet row identifier and use the ledger's URL history to update an existing row rather than creating duplicates. Internal surrogate IDs may still support database joins. Keep the database as the recovery record and treat the sheet as the editable view and control surface.
   - Support Excel as well: edit a workbook stored in OneDrive or SharePoint through Microsoft Graph, or provide an `.xlsx` export ([Microsoft Graph Excel API](https://learn.microsoft.com/en-us/graph/api/resources/excel?view=graph-rest-1.0)).

8. **Web control UI**
   - Provide a browser-based control plane for worker health, current activity, queue counts, recent errors, and the next scheduled run.
   - Offer clear controls for pause, resume, stop, and recovery. Pause prevents the next external browser action; stop ends the worker and leaves any unfinished application recoverable from its saved URL.
   - Show the application list, review queue, duplicate warnings, and audit history. Let the user edit job criteria, allowed sources, a target of new unique queue items (up to 200), and wakeup interval for each scrape job, plus the application's autonomy mode. Continue searching result pages until the target is reached or valid results/provider budget are exhausted; report the target and actual count for each run. Keep the Google Sheet as the editable tracker and link to it from the UI.
   - Include a headed-browser handoff view so the user can inspect a paused application, complete a human-only step, and resume from the checkpoint.
   - Show the active autonomy mode prominently: discovery only, prepare for review, or submit eligible applications automatically. The worker must pause for missing facts, uncertain duplicates, verification challenges, and site blocks.
   - Limit each user to one active browser session by default. Allow a per-user concurrency setting, bounded by host capacity. Make daily application limits configurable per user and show the remaining allowance in the UI.
   - Use only verified profile facts for application answers. Leave sensitive or unknown answers blank when optional; pause and ask the user when a required answer is missing.
   - Require per-user sign-in even on localhost. Provide an owner role for account and subscription management and member accounts for personal use.
   - Isolate every user's profile, application database, Google OAuth tokens, Sheets workbook, Gmail settings, Vaultwarden session, notifications, and browser profile. A user must never see another user's records or browser session.
   - Store integration secrets in separate per-user encrypted namespaces, including OAuth refresh tokens and Vaultwarden CLI credentials/session state. Keep encryption keys outside the application database in host-protected Docker secrets. Secret fields are write-only in the UI, with redacted logs and no secret values sent to the LLM or ntfy.
   - Use an individual Vaultwarden account or isolated vault per user, with a separate CLI profile and session. Never share one user's master password, API credentials, or unlocked `BW_SESSION` with another user's worker.
   - Bind to `127.0.0.1` by default. Offer an explicit `0.0.0.0` bind option with a prominent warning and required acknowledgment explaining that other devices on reachable networks can connect. Keep per-user authentication enabled for both modes; recommend a trusted LAN or VPN, firewall rules, and HTTPS for non-local access. Never return secrets in UI responses; mask credential fields and keep OTPs, passwords, and sensitive message contents out of logs and notifications.
   - Start VNC/noVNC only for an application browser handoff on CAPTCHA or sign-in verification. Bind ports to host loopback, show the direct browser-view link at the top of the owning user's queue and the temporary random password only on that user's authenticated queue-item history page. Keep discovery browser-free; the current applier supports one live handoff at a time.
   - Target a $10/month per-user subscription as a business requirement. Keep billing entitlements separate from account authentication; select a payment provider after deciding whether users access the same host locally or remotely.
   - Provide per-user data export and deletion. Deletion revokes Google and Vaultwarden credentials and removes the user's profile, browser data, and application history according to a documented retention policy.

9. **Vaultwarden integration**
   - Vaultwarden is compatible with Bitwarden clients, but it does not offer a stable, documented public API for arbitrary vault item management; its client API is compatibility-focused and may change ([Vaultwarden project discussion](https://github.com/dani-garcia/vaultwarden/discussions/4241)).
   - Use the Bitwarden CLI configured for the Vaultwarden server as the credential adapter. It supports creating vault items and connecting to self-hosted servers ([CLI create command](https://bitwarden.com/help/cli/), [self-hosted CLI configuration](https://bitwarden.com/help/change-client-environment/)). Verify a new item by reading it back before marking the save complete.
   - Give the worker a separate Vaultwarden account or isolated vault containing only job-site credentials. Keep unlock material in the secret store, restrict it to the vault adapter, and never log or send passwords through ntfy. Generate unique passwords and save them only for accounts the user approved.

10. **24/7 operations**
   - Supervise the scraper and applier as separate restartable workers; run Gmail sync independently. Apply bounded retries, per-site limits, per-user concurrency, redacted logs, health alerts, and fair queue scheduling.
   - Provide a pause control and a way for a person to resume a browser session after a handoff.
   - Use Docker Compose for workers and the ntfy server. Discovery and application workers run as separate always-on services; the Gmail metadata worker remains opt-in. Multi-user queue-triggered notifications remain to be built.
   - Before onboarding multiple users, move the current single-user application tables and secrets into per-user isolated stores and scope every worker job, API request, browser session, and notification to its owner.

## Suggested rollout

The control UI, discovery, matching, persistence, Gmail tracking, spreadsheet, guarded CDP submission path, and application-only browser handoff are implemented. Continue with stronger site-specific form support, queue-triggered notifications, and multi-user Gmail/Sheets/Vaultwarden integrations before broadening unattended operation.

## Deferred: per-job resume tailoring

- Let a user provide approved experience facts and a resume template in LaTeX, DOCX, or Google Docs. For a specific job posting, create a separate tailored copy by selecting, ordering, and rewording only those approved facts; never invent qualifications or overwrite the master resume.
- Render each draft to PDF and read the actual page count (for example, with `pdfinfo`). Revise within a configurable one- or two-page limit, using a bounded number of attempts and keeping the document readable. Flag a draft for review if it cannot fit without removing material the user needs.
- Show the rendered PDF and source changes for user approval before attaching or submitting it. Keep each approved version associated with its job and user. This workflow is deferred and is not part of the current resume upload feature.

## Current implementation status

- A containerized local control UI now provides owner setup, account sign-in, member creation, separate per-user SQLite ledgers and queues, encrypted candidate profiles, review controls, and saved worker preferences. The profile form accepts ordinary fields and repeatable entries, infers unknown from blank values, and keeps reuse policy internal. Resume upload and pasted primary text are supported; PDF, DOCX, and TXT text extraction runs locally, encrypted originals are retained per user, and explicit contact/summary/skill suggestions remain draft facts until profile approval. Uploaded files can be classified as primary or role/region-targeted and approved individually; previously saved text-only versions remain visible read-only.
- The queue records exact full URLs, duplicate warnings, leases, audit events, and recovery states. Public discovered listings also enter a separate shared global pool by exact URL; the UI lets each account add a pooled listing to its private queue. The **Apply queue** also accepts manually added full job URLs. Manual listings share only with explicit opt-in. Confirmed collection pages are skipped in the private queue and hidden from the pool without erasing their URL or audit history. The queue has a lease-bound invalid-URL handoff that requests a durable one-job rescrape and pauses that user's item. The discovery worker rechecks a request only if an enabled permitted source covers the same host, robots.txt allows it, and the exact URL yields a JobPosting. Each account can manage encrypted keyword searches and job-title source settings in Settings. Every newly discovered listing receives an advisory score from a local EmbeddingGemma 2 text-only model (270M parameters) when saved searches or approved ranking preferences exist; score failure leaves the listing in the queue with a reason. The model export verifies its loaded and saved text parameter counts, then removes the full Hugging Face download cache. The discovery worker uses `gemma4:e2b` to classify public search results, requires current profile approval, and requires discovery to be unpaused for ordinary scans. A separate always-on application worker claims eligible jobs for approved accounts, checks robots.txt, and opens public pages in headed Chromium through loopback CDP. In submit-eligible mode it uses local `gemma4:e4b` to interpret form labels and map them to relevant approved profile facts and answer-bank entries, then attaches the approved primary resume to a clearly labeled resume field. It may phrase an answer from supplied facts but cannot invent or infer facts, and receives no credentials, passwords, OAuth tokens, or other secrets. It rechecks profile/resume approval, pause state, and daily limit immediately before submission (`-1` means unlimited); there is no per-host allowlist. It marks an item applied only after a recognized confirmation page. Unknown required facts, ambiguous forms, legal attestations, high-risk disclosures, challenges, and uncertain outcomes go to review. A person can explicitly confirm a manual-handoff submission after completing it on the employer site. On a CAPTCHA or sign-in verification, the applier retains that user's application browser. The direct VNC/noVNC link appears at the top of that user's Apply queue and on the job's history page, with the temporary password only on the history page; only one handoff is active at a time. Discovery has no VNC server or ports. Multi-user queue-triggered notifications remain future work.
- The existing Gmail metadata worker, Google Sheets tracker, and Vaultwarden CLI setup remain single-user adapters for the original owner. They are not connected to member accounts or the web UI.
- The discovery worker supports per-user keyword searches via SearXNG and optional Adzuna, per-user configured RSS/Atom feeds or permitted public job pages, and the local OpenAI-compatible `gemma4:e2b` classifier for SearXNG results. Every new listing is scored by the text-only EmbeddingGemma ranker from saved searches and approved soft preferences. Each Scrape jobs entry has its own target for new unique queue items (up to 200) and cadence, plus a durable **Run now** request that the worker picks up on its next pass. Web searches scan more result pages as needed, up to 50 pages per title, and report the target and actual count; fewer valid postings or provider request caps can still leave a shortfall. SearXNG and Adzuna request caps are enforced per request page, including for on-demand runs. Adzuna credentials are encrypted per user; its terms and coverage limit this connector. The application worker uses local `gemma4:e4b` to interpret browser forms against relevant approved facts; it pauses for unknown required answers, signatures, legal attestations, sensitive high-risk requests, and verification challenges. JavaScript-only board discovery, source-specific board adapters, robust site-specific forms, per-user Gmail/Sheets/Vaultwarden credentials, queue-triggered notifications, and subscription billing remain to be implemented.
